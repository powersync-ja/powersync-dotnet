# Context: optimising the `get-api-rework` query path

This brief is for an agent tasked with improving the performance of the `Get`/`GetAll`/`GetOptional` implementation on the `get-api-rework` branch of powersync-dotnet ([PR #107](https://github.com/powersync-ja/powersync-dotnet/pull/107)). It covers:
- the goal and the constraints,
- the hot path as it stands,
- the baseline numbers and how to measure.

## Goal

PR #107 replaces the Dapper-based query API with `SqlMapper<T>` delegates, `IFromRow<T>` (hand-written or generated by `[GenerateSqlMapper]`) and an untyped `QueryResult`/`IQueryRow` API. The PR claims the new API "should (pending benchmarks) make the query API faster". **The benchmarks currently say the opposite for bulk reads.**

Targets, in priority order:
1. **Bulk `GetAll<T>`** through `[GenerateSqlMapper]` and hand-written `IFromRow<T>`: at least match the old Dapper path (ratio ≤ 1.00 vs `0.1.5` typed) at 10k, 100k and 1M rows, and allocate no more than it.
2. **Untyped `GetAll` (`QueryResult`)** and the **`SqlMapper<T>` delegate path**: improve them as far as their API allows.
3. **Single-row `Get`**: must not regress. It is already slightly faster than Dapper.

## Constraints

- **Keep the PR's public API working.** It consists of:
  - `IQueryRow` with by-name (or by-position) getters (`GetString`, `GetLong`, `GetBool`, `GetDouble`, `GetDateTime`, `Get*OrNull`, `GetValue`, `Columns`);
  - `QueryResult` (`Rows`, `Count`);
  - `SqlMapper<T>` and `IFromRow<T>` (`static abstract FromRow(IQueryRow)`);
  - all `Get`/`GetAll`/`GetOptional`/`Watch` overloads on `IDBGetUtils`, `PowerSyncDatabase` and `IPowerSyncDatabase`.

  Public API changes:
  - Purely **additive** changes are allowed when they pay off clearly, for example ordinal getters or a way to resolve column ordinals once. List each one in your report.
  - **Breaking** changes, including semantic ones, need human sign-off. Propose them; don't apply them.
- **Keep the getter semantics:**
  - column-name lookup is case-insensitive;
  - `Get*` throws `InvalidOperationException` on NULL and `ArgumentException` on an unknown column;
  - `GetBool` accepts 0/1 integers;
  - `GetDateTime` parses strings with `InvariantCulture` + `DateTimeStyles.RoundtripKind`;
  - numeric conversions behave like `Convert.ToXxx(…, InvariantCulture)` for the value types SQLite returns (`long`, `double`, `string`, `byte[]`).
- **Row lifetime is a semantic question.** Callers can currently keep `IQueryRow` instances: `QueryResult.Rows`, `Get` returning an `IQueryRow`, `row => row` mappers. A "cursor" row that is only valid while its mapper runs would change that. That is fine for the typed `GetAll<T>`/`IFromRow` paths only if the row cannot escape. Flag the trade-off explicitly.
- **AOT and trimming safety.** iOS/MacCatalyst support is one of the motivations for removing Dapper, so add no `Reflection.Emit`, no runtime code generation and no `dynamic`.
- **PowerSync.Common uses `LangVersion` 12.** It targets `net8.0;net9.0;net10.0`, Android, and iOS/MacCatalyst on macOS. Don't use C# 13+ features or APIs newer than net8.0 without `#if`.
- **The source generator** (`PowerSync/PowerSync.Common.SourceGenerators/SqlMapperGenerator.cs`, netstandard2.0, Roslyn 4.8) may emit different code. Its emitted-text assertions in `Tests/PowerSync/PowerSync.Common.SourceGenerators.Tests/SqlMapperGeneratorTests.cs` will then need updating, and generated code must only use public PowerSync.Common API.
- **Don't change the existing benchmarks to make numbers look better.** If you add an API worth measuring, add a *new* benchmark method in `src/Bench.Rework` and keep the existing ones as they are.
- Don't commit, push or comment on the PR unless the human asks. Work on the `get-api-rework` working tree, or a branch off it.

## The hot path today (`get-api-rework`)

Call chain for `db.GetAll<T>(sql)` where `T : IFromRow<T>`:

1. `PowerSyncDatabase.GetAll<T>` (`PowerSync/PowerSync.Common/Client/PowerSyncDatabase.cs` ~L784–794) calls `await WaitForReady()`, then `Database.GetAll<T>(…)`.
2. `MDSQLiteAdapter.GetAll<T>` (`MDSQLite/MDSQLiteAdapter.cs` ~L212–219) leases a pooled read connection with `await ReadLock(ctx => ctx.GetAll<T>(…))`.
3. `MDSQLiteConnection.GetAll<T>` (`MDSQLite/MDSQLiteConnection.cs` L193) calls `GetAll(query, parameters, T.FromRow)`.
4. That overload runs `Task.Run(() => ReadRows(query, parameters).Rows.Select(row => mapper(row)).ToList())` (L188–191).

`ReadRows` (`MDSQLiteConnection.cs` L149–175):
- Builds a case-insensitive `Dictionary<string,int>` of column indices once per query.
- Then, **for every row**:
  - allocates a new `object?[FieldCount]`;
  - calls `reader.IsDBNull(i) ? null : reader.GetValue(i)`, which boxes every `long`/`double`;
  - allocates a `QueryRow`;
  - adds it to a `List<IQueryRow>` that is not pre-sized.
- **The whole result set is loaded before any mapping happens.** The mapped `List<T>` is then built from it.

`QueryRow` (`DB/QueryRow.cs`) handles each column read like this:
- `GetValue(name)` does a dictionary lookup with `StringComparer.OrdinalIgnoreCase`;
- `GetRequired` adds a null check;
- the conversion is `Convert.ToInt64/ToDouble/ToBoolean(object, InvariantCulture)` or `Convert.ToString(object)`;
- `GetDateTime` calls `DateTime.Parse(s, InvariantCulture, RoundtripKind)`.

What the generated mapper (`[GenerateSqlMapper]`) emits for the benchmark type:
```csharp
return new TodoGenerated {
    Id = row.GetString("id"), ListId = row.GetString("list_id"), Description = row.GetString("description"),
    CreatedAt = row.GetDateTime("created_at"), CompletedAt = row.GetDateTimeOrNull("completed_at"),
    Completed = row.GetBool("completed"), Quantity = row.GetLong("quantity"), Price = row.GetDouble("price"),
};
```

**Why the old Dapper path wins on bulk reads:** Dapper reads straight from the `DbDataReader` using typed getters and column ordinals, resolved once per query. It builds each `T` while streaming, with no intermediate row objects and no boxing of the values it reads into typed properties. Its overhead is a buffered list followed by `.ToArray()`.

**Other consumers of `QueryResult`/`IQueryRow`** that must keep working:
- `Watch(...)`: `PowerSyncDatabase.cs` ~L875–890 re-runs `GetAll` on every change.
- `GetSourceTables` reads `EXPLAIN` output via `QueryResult.Rows`.
- `SqliteBucketStorage.cs` L115/L146 reads `rs.Rows[0].GetLong("seq")`.
- `CrudEntryJSON.FromRow` and `Attachment.FromRow` are `IFromRow`-style mappers.

**Other per-call overhead**, which matters for single-row `Get`:
- `WaitForReady()`, `ReadLock` (channel-based pool) and `Task.Run` on every call;
- `PrepareQueryString` rewrites every `?` into `@paramN` with a `StringBuilder`, and parameters are created per call;
- `Get`/`GetOptional` go through `ReadRows(limit: 1)`, which still builds the column dictionary and a `List`.

## Hypotheses worth testing

These are not prescriptions. Measure each one, because some may not pay off.
- **Typed `GetAll<T>`/`IFromRow`/mapper overloads:** map while streaming instead of loading `List<IQueryRow>` first. For example, pass the mapper an `IQueryRow` view over the live `SqliteDataReader` with values cached per row, and drop the per-row `object?[]` and `QueryRow`. Check the row-lifetime constraint above.
- **Remove boxing and `Convert`.** Use type-specific fast paths, for example `value is long l ? l != 0 : Convert…` for bool, `value as string ?? Convert.ToString(...)`, and `reader.GetInt64/GetDouble/GetString` when reading from the reader directly.
- **Avoid a case-insensitive hash for every column read.** Options:
  - a small per-query ordinal cache with an ordinal-equality fast path;
  - an additive `int GetOrdinal(string)` plus ordinal getters, which the generator could use after resolving ordinals once per result set (this needs a public API addition, so flag it).
- Use one `GetValue` and check for `DBNull`, instead of `IsDBNull` followed by `GetValue`.
- Pre-size lists where the count is known. Avoid the LINQ `Select(...).ToList()` closure.
- Cheaper date parsing for ISO-8601, for example `DateTime.ParseExact` with the known formats or a span-based parser, while keeping `RoundtripKind` results identical.
- For single-row `Get`: avoid the `List`/dictionary in `ReadFirstRow`, and look at reusing commands and parameters.

## Baseline numbers

These come from a `--quick` run (1 warmup + 3 iterations), so treat them as indicative. Host: Apple M4 Pro, macOS 27.2, .NET 9.0.2 (Arm64), BenchmarkDotNet 0.15.8. The ratio is relative to the 0.1.5 typed Dapper row in the same table.

| GetAll | 0.1.5 typed (Dapper) | 1.0.1-dev.3 typed (Dapper) | rework (all 4 styles) |
|---|---|---|---|
| 10,000 rows | 17.35 ms, 4.83 MB | 16.51 ms | 20.6–20.8 ms (1.19–1.20), 5.94 MB |
| 100,000 rows | 177.2 ms, 47.8 MB | 169.2 ms | 209.7–211.0 ms (1.18–1.19), 58.8 MB |
| 1,000,000 rows | 1.877 s, 474 MB | 1.878 s | 2.25–2.34 s (1.20–1.25), 584 MB |

| Single-row Get (1M-row table) | Mean | Allocated |
|---|---|---|
| 0.1.5 typed (Dapper) | 24.2 μs | 4.87 KB |
| rework, source-gen / delegate | 21.8 μs | 4.22 KB |
| rework, manual `IFromRow` / `QueryResult` | 23.1–23.9 μs | 4.22–4.31 KB |

What these numbers show:
- All four rework styles have **identical allocations** and nearly identical times. Mapping style is not the cost; the shared `ReadRows` materialisation is.
- The old `dynamic` + manual path (≈ 1.05–1.07) is closest in structure to the rework, since it also builds intermediate rows. It is still faster.
- Run-to-run noise on this machine is a few percent, and single-row results can be bimodal. Don't trust differences under ~5% from `--quick` runs.

## How to measure

All commands run from `/Users/luc/work/powersync-ja/dotnet-get-api-bench` unless stated otherwise.

1. **SDK unit tests.** Run these after each change, from the powersync-dotnet repo. Integration tests need a server, so skip them.
   ```sh
   dotnet test Tests/PowerSync/PowerSync.Common.Tests --framework net9.0
   dotnet test Tests/PowerSync/PowerSync.Common.SourceGenerators.Tests --framework net9.0
   ```
2. **Pack your working tree into the local feed.**
   - The script includes uncommitted changes and marks them `-dirty`.
   - It writes `ReworkVersion.props`, which pins `src/Bench.Rework` to the new package.
   - Each pack gets a new version, so the first benchmark after a pack re-seeds its DBs, which takes about 8 seconds.
   ```sh
   scripts/pack-rework.sh
   ```
3. **Correctness check.** This must print `All validations passed.`, because it checks every field of every row at each size:
   ```sh
   dotnet run -c Release --project src/Bench.Rework -- --validate
   ```
4. **Iterate quickly** on the rework only. The 100k-row case is a good proxy.
   ```sh
   dotnet run -c Release --project src/Bench.Rework -- --quick --filter '*GetAll_SourceGen*'
   dotnet run -c Release --project src/Bench.Rework -- --quick --filter '*'
   ```
5. **Final comparison** against 0.1.5 and 1.0.1-dev.3, using full iterations. Results go to `results/summary.md`.
   ```sh
   scripts/run-all.sh
   ```
   To skip re-running Legacy, run the Rework project with `--artifacts BenchmarkDotNet.Artifacts/<new-dir>/rework`. Then copy in a previous `legacy` folder and run `dotnet run scripts/combine.cs -- BenchmarkDotNet.Artifacts/<new-dir>`.

Benchmark details worth knowing:
- Every style runs the same SQL: `SELECT id, list_id, description, created_at, completed_at, completed, quantity, price FROM todos`.
- The query reads a PowerSync view, so each column is a `json_extract` from `ps_data__todos`.
- `completed_at` is NULL on odd rows. The values are deterministic; see `shared/TodoData.cs`.
- The SQLite + view cost is the same for every version, so improvements can only come from the .NET side.
